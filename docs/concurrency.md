# Concurrency comparisons

Use **Results**, then **Graphs & comparisons**, to examine saved benchmark results. The control panel is made of toggle buttons. Tick the metrics to draw, the models to include, and colour the curves by model or by benchmark. **Plot against** chooses the horizontal axis.

With **Prompt length** on the axis, the recorded query counts appear as toggles and each ticked count draws its own line, so one query and eight queries can be read on the same chart. With **Concurrent queries** on the axis, the recorded prompt lengths become the toggles instead. Five 20k prompts are a different workload from five 40k prompts, so each prompt length stays a separate line. Until you choose otherwise, every recorded value is ticked while that keeps a chart to eight lines or fewer, and one model on one benchmark is coloured by query count or prompt length. Only values that were actually recorded are offered, and the concurrency axis is unavailable when a selection recorded a single query count. These views launch no inference.

Changing the axis never changes which metrics are ticked or how they are defined. A metric that was not recorded for the selection is marked on its button and listed above the charts rather than replaced by another. Distinct recorded row configurations of the same model retain separate curves and labels rather than becoming a shared repeat median. Below the concurrency charts, a collapsed section holds the model-by-query-count map and each request's timing.

## Read throughput and latency together

Use the metric selector for group output throughput, prompt-processing rate, first-token wait, response duration, whole-batch completion time, matched throughput gain or measured energy. Group output throughput is total output tokens divided by batch elapsed time, including prefill and queueing. Recorded per-request decode speed is a separate measure; it must not be interpreted as total system throughput. Range whiskers describe observed request durations, not confidence intervals.

Expand **Concurrency map and request evidence** for the detailed model-by-request-count matrix and raw requests. The map uses the selected metric. Colors are relative within each row; use the printed values for comparisons between rows. Failed/timed-out, skipped/cancelled, unmeasured and unavailable cells have distinct labels. An asterisk marks estimated output counts. Missing cases are never zero-speed measurements.

Select a map cell or chart point to inspect request evidence: actual prompt/output counts, TTFT, decode rate, completion duration and status. Timing bars separate the wait for first output from the subsequent response interval, including scheduler pauses. Recorded dispatch offsets place timings relative to batch start; missing historical offsets are not inferred. The graph's visible legend identifies configuration, model, engine and GPU where recorded.

## Compare recorded execution conditions

Models, quantizations, engines, reasoning, MTP, KV precision, endpoint identities and recorded GPU offload remain separate conditions. GPU offload is printed in the legend/map when recorded. A partial-offload condition can include substantial CPU work and must be distinguished from full-GPU execution. Unreported settings remain unknown; the dashboard cannot authenticate the underlying weights or effective provider settings.

Successful complete groups contribute to median throughput and latency. Concurrent completeness requires a recorded completed-request count or a full set of successful request records; otherwise the group is labeled unverified. Failed, incomplete and unverified groups remain inspectable, including their surviving requests, but do not count as successful scaling or capacity. Throughput gain and decode retention pair successful repeat IDs with an equivalent one-request baseline, prompt target, per-request context allocation, placement and power scope. Unmatched repeats and estimated output counts do not produce a measured scaling claim.

The **End-to-end output throughput** metric uses total output tokens divided by group elapsed time for every query count, including one request, with prefill and queueing included. **Total decode throughput** instead divides scoped decode tokens by the union of post-first-token decode intervals, excluding TTFT and gaps outside those intervals. This makes its one-request baseline comparable to concurrent batches; per-stream decode rate remains a separate measure. It is never the sum of per-request decode rates. After-first-token decode includes waiting while other prompts are processed; backend prompt-evaluation timing, when reported, is separate. See [Measurements and sessions](measurements.md) for exact timing and token scopes.

GPU energy includes prompt processing and uses the shared group measurement once. The energy chart requires known scope, complete GPU power coverage and actual output counts; missing or low-confidence energy stays unavailable. Per-card measurements and global integration boundaries are described in [Measurements and sessions](measurements.md#hardware-power-and-provenance).

Use **Export visible graphs (SVG)** to save the displayed graph, or **Tables & CSV** for numerical observations. JSON export retains original observations. Comparing saved results changes no historical data. See [Sharing results](sharing-results.md) to publish reviewed datasets.
