# Browser mode

Open [Wattever on GitHub Pages](https://lpalbou.github.io/Wattever/) to run a quick benchmark without installing Wattever. Start LM Studio or another OpenAI-compatible server with models available. Enter its endpoint (the default is `http://localhost:1234/v1`) and select **Connect**; Wattever does not request the model list until you connect. Choose models and workloads, start the benchmark, and keep the page open until it finishes.

The provider must permit cross-origin requests. LM Studio has an Enable CORS switch in its [server settings](https://lmstudio.ai/docs/developer/core/server/settings). Browsers may also require local-network permission, and HTTPS-to-localhost behavior depends on the browser and its security settings; see [Microsoft Edge local network access](https://learn.microsoft.com/en-us/deployedge/ms-edge-local-network-access). Wattever connects directly from the browser: it has no hosted proxy and does not use helper credentials. If the endpoint needs an API key, enter it in the page; the key stays in memory and the input clears after connecting. It is not saved in result files or browser storage.

Endpoint names and route IDs are automatic. Recognized official cloud hosts or explicit service metadata can identify the service; otherwise a Local/Private/Remote endpoint fallback is used. No manual label or ID is required, and an advanced **Display name** override is optional. Canonical known public API routes use stable public provider IDs; other routes, including custom cloud paths, use a private URL-to-random-ID mapping in browser local storage. That mapping is excluded from exports; clearing storage can regenerate its IDs. Detection describes the route/provider, not verified inference hardware or backend weights.

Chrome versions with separate network permissions may call localhost access **Apps on device** or **Loopback network**. Allow the permission for the Wattever site when you connect. The permission is distinct from access to other devices on your LAN; see [Chrome local network guidance](https://github.com/GoogleChrome/modern-web-guidance/blob/main/skills/modern-web-guidance/guides/security/local-network-access.md).

GPU, CPU, RAM and VRAM fields are optional user-supplied descriptions, not hardware discovery. Browser mode cannot measure GPU power or VRAM use, load/unload models, choose placement, allocate context, control MTP, resume a session or extend the same file. It can request standard reasoning effort, temperature and the supported token-limit field; the engine's effective behavior remains unverified. Unsupported request values fail visibly. Configure model execution in the provider. Use the [local helper](getting-started.md) for detected client hardware and optional local telemetry; its managed LM Studio provider additionally supports lifecycle/context controls and same-file extension.

New browser results record `measurement_mode: browser`, `browser_schema_version: 2` and protocol `browser-2`, with bundled corpus identity and a SHA-256 hash when available. Timing includes network/browser overhead and is not directly comparable to helper protocols. Exact provider usage is required for token throughput; missing counts remain unavailable, with no character/chunk token estimate. Reasoning usage and observed output boundaries are recorded: reported unstreamed reasoning is excluded from decode, ambiguous hidden reasoning or a single output event leaves decode unavailable. Prompt tokens/client TTFT remains a proxy including possible hidden work, not isolated engine compute. Public model configuration fingerprints distinguish requested/reported/unknown settings without storing connection URLs. Historical `browser-1` files remain readable and may include estimated throughput; compare their protocol/provenance separately.

Results are stored in browser storage and can be downloaded or imported as JSON. Storage can be cleared or unavailable; if a storage warning appears, download the in-memory results before closing the page. Closing or reloading the page stops the browser benchmark, and a previously running result is shown as interrupted. On timeout the browser aborts its requests and stops the run, but cannot verify that the provider stopped inference or unload its model. Check the provider before starting another workload. Helper benchmarks instead continue in the local server when the page closes; see [measurements and sessions](measurements.md).

Results also shows a read-only shared catalog without requiring an endpoint connection. Hiding a shared result affects only this browser. See [sharing results](sharing-results.md) to contribute a benchmark.

## Shared-results data boundary

The hosted site opens the shared Results library by default. Browsing it reads only the same-origin GitHub Pages catalog and benchmark JSON; it does not query desktop helper APIs or local files. Shared records identify their GitHub source. The published JSON omits host-local diagnostic text and paths while preserving measurements, failure classifications, hardware descriptions, settings and session provenance. It is a public projection of the repository record.

If the browser data client fails to load, the hosted site reports that failure rather than falling back to desktop APIs. Model-server access belongs to the optional Run workflow and starts only after an explicit Connect action.

The **Capabilities** library reads same-origin shared capability files, verifies their catalog SHA-256 and supports export/comparison. Dataset/score validation occurs during publication with the helper's deterministic re-scoring and fingerprint checks. The hosted page cannot launch capability tests or import unvalidated capability files; use the helper for those actions. Throughput JSON import remains available in browser Results. See [capability evaluation](capabilities.md).
