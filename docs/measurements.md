# Measurements and sessions

The local helper supports managed LM Studio and generic OpenAI-compatible endpoints. Hosted browser mode uses a separate `browser-2` protocol; historical `browser-1` files remain readable. Browser/helper timings and historical estimates are not directly interchangeable. See [Browser mode](browser.md).

## Throughput and timing

A case combines a model, technique, prompt size, simultaneous query count and repeat. Successful, failed and skipped cases are recorded; inability to load or fit a workload is useful capacity information. The library reports successful, failed, skipped and cancelled counts separately; an unattempted skipped repeat is not counted as a measured failure. Managed LM Studio can schedule Standard/MTP modes when a supported bundled MTP head exists, and disables reasoning by default. Generic endpoint technique, reasoning, context allocation, KV cache and quantization are controlled by the inference engine. Their effective state is unknown unless documented separately by the operator; a scheduler technique label does not prove the server's MTP state.

When a provider supplies per-request `draft_n` and `draft_n_accepted` timing
counters, Wattever retains validated nonnegative integer counts. Missing
counters remain unknown. Acceptance cannot exceed the offered count; requested
drafting and observed proposals remain separate evidence.

For one request, client timings use a monotonic clock with these boundaries:

| Metric | Boundary / calculation |
|---|---|
| `ttft_s` | Request start to first observed nonempty content or reasoning output. This is the client prefill proxy; queueing and network time are included. |
| `decode_s` | First observed nonempty output to **last observed nonempty output**. Prefill/TTFT and trailing usage, finish markers or EOF delivery are excluded. |
| `response_tail_s` | Last observed output to completed stream delivery. This is separate from generation time. |
| `wall_s` | Request start through completed response delivery, including all phases and transport tail. |
| `prefill_tps` | Prompt tokens divided by client prefill-proxy time. |
| `decode_tps` | Scoped decode tokens divided by decode time; **never** divided by end-to-end wall time. |
| `group_output_tps` | Total completion tokens divided by end-to-end wall time; this is a separately labeled end-to-end rate. |

A single output event has no observed interval between output events, so decode throughput is unavailable. Delaying usage or EOF packets must not lengthen decode time. Backend-reported engine counters remain in `reported_timings` and are not substituted for client timings. Client TTFT does not isolate the instant an engine receives or starts processing a prompt; pure engine prefill requires backend evidence.

For concurrent requests, retain each request's start offset from the common batch clock. Total decode throughput is the sum of scoped `decode_token_count` values divided by the **union** of successful requests' post-first-token decode intervals. Overlapping intervals count once; gaps in which no request is decoding are excluded. A sum of request rates can overstate serialized work, and whole-batch wall time wrongly includes prefill. The prefill proxy similarly uses the union of request-start-to-first-output intervals. These observed proxy intervals can include queueing and another stream's decoding; they are not isolated engine compute intervals. Concurrent phase unions can overlap, so their durations must not be added to reconstruct batch wall time.

Concurrent `wall_s` runs from batch dispatch through the final request's completion. The TTFT shown per request is its median across requests, distinct from the total prefill-proxy interval. Successful complete groups contribute to comparison charts; failed and incomplete groups retain inspectable partial evidence without being treated as successful throughput. Missing offsets, durations or scoped counts leave derived phase rates unavailable.

Server token usage supplies the output numerator. Hidden reasoning reported by the server is excluded from the scoped decode count when it was not streamed; unknown hidden work remains explicitly uncertain. No token rate is inferred by counting characters or stream chunks. The conventional first-token correction subtracts one token from scoped usage. Because the first received chunk can contain several tokens, its exact token boundary is unknown; `timing_scope.decode_count_estimated_boundary` records that approximation and decode plots/tables mark it. Live progress can report **chunks/s**, explicitly separate from final tokens/s.

`timing_scope` records output kinds, reasoning usage provenance, first-chunk uncertainty and the decode end boundary. New records identify the last observed output boundary. Historical records can contain first-output-to-EOF durations; without a recorded last-output timestamp their transport tail cannot be recovered. Those derived decode values remain marked approximate. Historical raw observations are preserved rather than silently rewritten. Exported derived fields retain recorded values and sources for audit.

Results exposes total decode throughput, median per-request decode, decode time, client-prefill-proxy time, and end-to-end output throughput as separate metrics. Axis switches preserve a metric's meaning or explicitly disable an unsupported combination. CSV includes scoped counts, request timing evidence and provenance. GPU decode energy covers the same first-to-last-output window as decode throughput. Whole-case GPU energy uses its independently sampled full-request window; it is not fabricated by adding incomplete or differently bounded phase windows. Provider-reported prompt/decode counters stay separate.

## Context and workload

For managed LM Studio, the default per-test allocation reserves prompt tokens, output budget, 512 tokens of headroom and a 5% prompt safety margin, subject to the model's per-request maximum. Shared KV allocation multiplies per-request capacity by concurrency. The per-test policy reloads for each context/concurrency allocation; the optional fixed policy uses the largest planned allocation per model and MTP mode, reducing reloads while changing memory conditions. Generic endpoint context estimates describe client workload planning only; configure the real context/KV allocation in the engine. More concurrency consumes more memory; large contexts can fail to fit.

In Benchmarks and Add / rerun tests, select each prompt size and concurrent query count independently; selecting a larger value does not add smaller values. The selected sizes and query counts form the workload combinations. Prompt presets are 512, 5k, 10k, 20k, 40k, 80k, 100k, 120k, 150k, 200k and 260k tokens; concurrency presets are 1 through 10, 15, 20, 30, 40, 50, 75 and 100. Compare cases at matching dimensions, output budget and repeat count. Close competing workloads and record relevant clock/power settings and runtime placement.

## Hardware, power and provenance

NVIDIA telemetry uses one `nvidia-smi` process to sample every detected NVIDIA card. New runs retain each card's board power, utilization, used/capacity VRAM, temperature and SM clock, plus combined GPU totals. Power and physical VRAM usage are summed at the same monitor timestamps; utilization is an unweighted mean, temperature is the maximum reported value, and separate clocks remain per card. Summed physical VRAM does not imply pooled allocations. Missing/stale readings make the corresponding complete aggregate unavailable. macOS may use `powermetrics` for GPU and CPU rails with permission; these have different boundaries. Whole-system power remains an estimate: combined GPU power plus CPU and other-system estimates, counted once. Primary GPU selection identifies the benchmark; it does not restrict monitoring or select inference placement. Generic endpoint power is unavailable unless `endpoint_inference_local: true` explicitly asserts that inference runs on the benchmark client. An externally loaded model prevents a verified unloaded-model idle baseline. Historical selected-card measurements retain their original scope and are never reconstructed as all-card totals.

Hardware inventory is a best-effort, read-only snapshot of the benchmark client, not verified remote server hardware. Additive `metadata_schema_version: 1` metadata accompanies result `schema_version: 2`; historical files remain readable. Available fields include CPU/socket/core counts, RAM modules and reported clocks, GPU VRAM/driver, and current/max-reported PCIe generation and width. DIMM count does not establish active channels. PCIe snapshots can downshift while idle; reported maxima may reflect platform limits. `link_encoding_ceiling_bytes_per_second` is a derived one-direction ceiling after encoding only, excluding packet/system overhead. It is neither a measured DMA rate nor device-memory bandwidth. Unmeasured bandwidth remains null.

Memory topology is collected automatically without installing utilities. Windows reads SMBIOS through `GetSystemFirmwareTable`: populated Type 37 channel records take precedence; explicit Type 17 channel/slot labels provide a separately labeled firmware-layout inference. Linux uses populated EDAC channel locations where available. Other or incomplete reports remain unavailable. Raw firmware identifiers and slot labels are not retained. `memory.channel_topology` records the source, method, timestamp, populated channel count and independently detected active count, if supplied. **Populated channels do not prove the active controller interleave mode.** No count is inferred from DIMM quantity, CPU maximum specifications or bandwidth.

**This machine** and result badges distinguish firmware layout, OS reports and controller detection. **Refresh memory topology** runs the built-in probe. A later annotation on matching GPU, CPU, motherboard, RAM capacity and reported clocks retains its capture time and marks historical inference conditions unverified; original sessions and inference rows stay unchanged. Pending configuration checks prompt when their benchmark's GPU is reconnected. Channel counts and provenance are included in helper CSV exports.

Helper throughput benchmarks run separate transfer microbenchmarks before inference by default. The API's `hardware_probe_policy: "defer"` skips fresh probes and reuses only a verified matching saved capture, or records that the measurement is deferred. Reused captures retain their original timestamp and are not presented as measured in the new session. Capability evaluations always use this separate-probe policy, keeping RAM, storage and CUDA microbenchmarks outside accuracy collection. **Measure transfer bandwidth** in the machine panel runs them independently. Choose **Storage test folder** on the drive holding your weights, or leave it blank to test the results volume; the folder path is excluded from saved public configuration. Storage → RAM reads a flushed 256 MiB temporary file three times in 8 MiB blocks at queue depth one, bypassing the OS page cache with Windows unbuffered I/O, Linux `O_DIRECT` or macOS `F_NOCACHE`. Device/controller caches may still contribute. File creation is excluded from read timing, and the temporary file is removed. This is sequential read throughput on the selected filesystem, not random expert-fetch performance or a measurement of other drives.

RAM → VRAM probes each detected NVIDIA adapter sequentially, mapped by PCI bus through the CUDA driver. Each device result retains its identity, raw samples and PCIe snapshots before and during untimed transfer warmup in `ram_to_vram_devices`. The selected primary adapter's result also appears in the compatibility field `ram_to_vram`; selecting it does not restrict the device sweep. The probe times completed copies from a 64 MiB pinned host buffer, with warmup, three 2 GiB samples, synchronization and a readback check. It describes host-to-device transfers, not internal VRAM bandwidth or pageable-memory performance. Separate device rates are not measured simultaneous throughput, and physical slot labels/wiring remain unverified. The probe avoids starting when reported free VRAM is below 512 MiB. Unsupported hardware, insufficient resources and failed probes are recorded as unavailable rather than estimated. No inference models are loaded or unloaded by the probes. An isolated worker has a 75-second limit.

`hardware.transfer_bandwidth` records protocol `wattever-transfer-v1`, capture time, scope, method, raw byte/time samples and their median bytes/second; UI rates use decimal MB/s and GB/s. Throughput execution sessions retain their own profile. Generic remote endpoints characterize the benchmark client, not the inference server. Browser-only mode cannot perform these native probes. A later measurement can be attached to a saved benchmark only on matching hardware and GPU/driver; it is marked `measured_later_on_matching_hardware`, with historical inference conditions unverified. Original inference measurements and session metadata are preserved.

Optional `reproducibility` settings and `performance_claims` are user-reported public annotations kept separate from detected fields. Record engine/version, model revision, quantization, context, KV precision and MTP draft count when known, plus placement and competing workloads in reviewed notes. Wattever does not invent TFLOPS from GPU names or model quantization. A sourced compute claim must state arithmetic precision, execution path, dense/sparse behavior and whether it is an advertised peak, independent measurement or estimate. Integer INT4/INT8 claims use TOPS; floating-point FP4/FP8/FP16/BF16/FP32 claims use TFLOP/s. Quantized weight storage does not establish inference arithmetic precision.

Quantization storage format (`quantization`, such as `Q4_0`) is separate from the method (`quantization_method`, such as QAT, QAD or UD). LM Studio discovery combines its model catalog and display labels, and records `quantization_source` and `quantization_method_source`. Unknown methods stay unknown; a four-bit format alone does not establish QAT or post-training quantization. Results and model selection show both labels when available. Historical catalog annotations use `lmstudio_catalog_backfill`, which does not verify historical weight bytes.

Each result can also carry a public `model_configuration` and `configuration_id`. It distinguishes requested model alias, canonical checkpoint, automatically resolved opaque endpoint ID/display name, operator reports and control-plane evidence. Endpoint naming provenance is detected, inferred, operator override or unknown; it is not established by ports or model aliases. The private URL-to-ID registry is excluded from public outputs, and URLs are not hashed into route IDs. Unknown quantization, reasoning or MTP is explicit. A configuration hash verifies consistency of public fields; it does not verify endpoint weights, effective settings or inference location. Historical user-reported endpoint identities remain readable. Capability task accuracy uses a separate protocol/result family; see [capability evaluation](capabilities.md).

## Live telemetry and sustained observations

The helper samples whole-client CPU utilization and physical RAM usage independently of GPU sensor availability. The live dashboard shows combined GPU power/physical VRAM and a separate panel for each NVIDIA card. These measurements include competing processes and monitoring overhead; they do not isolate inference. Per-card VRAM percentage uses that adapter's capacity; combined occupancy uses summed used/capacity readings. CPU temperature is only ever an actual sensor reading, never an estimate. Linux may expose a CPU package sensor (hwmon `coretemp`, `k10temp` or `zenpower`). Windows has no unprivileged CPU package sensor, so the helper reads one only from a sensor tool that is already running: HWiNFO with Shared Memory Support enabled, or LibreHardwareMonitor with its web server on port 8085 (both report the CPU package, or Tctl/Tdie on AMD); otherwise Core Temp (the hottest core, labelled as such) or a live ACPI thermal zone (a firmware zone, not the CPU package, shown only once it has been seen to change because many boards report a fixed placeholder). `cpu_temp_source` names the source; when there is none, `cpu_temp_note` says why and the System view shows that reason. Missing temperatures remain null, including on macOS without an available temperature source.

RAM usage means physical total minus OS-reported available memory on Windows and Linux. macOS uses total minus free/inactive pages and labels that availability boundary as an estimate. CPU utilization uses host CPU-time deltas, not load average. GPU snapshots are held briefly while fresh; failed/stale sensors do not become zero utilization.

Stored `telemetry.history` contains elapsed seconds, UTC timestamps, scope and up to 3,600 recent points with explicit ring-retention counts. At 150 ms this covers roughly nine minutes; older points can be dropped. `telemetry.summary` preserves all-run observed sample means, time-weighted means, maxima, first/last readings and coverage despite history eviction. Raw phase samples retain up to 72,000 rows; a phase older than that retention is flagged incomplete.

All-card histories use scope `benchmark_client_all_nvidia_gpus`, with independent readings in each point's `gpus` array and per-card all-run statistics in `summary.gpus`. Single-query result `power.gpus` retains prefill/decode windows and energy per card; the existing scalar watt/joule fields now describe the declared combined boundary. Concurrent requests retain one whole-case `group_power` with per-card windows, avoiding overlapping energy double counting. The global VRAM peak is the peak of simultaneous sums, rather than the sum of independent card peaks. CSV exports include per-card columns and full per-card JSON. Covered all-run energy includes loading and idle; per-test energy is reported separately. Estimated CPU/system energy is always labeled as estimated.

Time-weighted coverage excludes long sampling gaps. Peaks are observed maxima and can miss shorter spikes. Early/late 60-second means can overlap on short runs. Changes in temperature, clocks or load describe the observed workload/environment; they do not establish throttling or prove sustained model throughput. Compare repeat throughput at matching workload and placement alongside thermal/load traces. Separate graphs per selected metric avoid sharing incompatible units on one chart.

## RAM and storage comparisons

Transfer profiles also measure native RAM copy payload throughput with one worker and several workers. Each worker uses disjoint 64 MiB source and destination buffers; committed pages, one warmup pass, three timed samples and readback checks are included. The working set exceeds typical CPU caches. Reported bytes count copied payload: logical source reads plus destination writes equal twice that count, while actual DRAM traffic depends on caching and write allocation. This is a copy microbenchmark, not peak DRAM bandwidth or a channel-count measurement.

In Machine details, use **Additional storage folders** to compare drives during the same measurement; separate existing folders with semicolons. Each volume gets its own temporary unbuffered read test and raw samples. The selected primary volume remains separate. Paths stay private; volume letters, available device model names and measured rates can be shared. Inference may benefit differently because model loading, mmap faults, OS caches and CPU/GPU overlap affect its I/O.

Execution sessions retain their hardware snapshot and transfer profile, including reported RAM clocks. Later independent captures remain available in **Independent hardware measurements**. This preserves conditions across storage or memory-setting experiments.

The collapsed **This machine** header shows CPU, GPU, RAM and per-card VRAM. Expanded Run and saved Results inventories use the same grouped compute/memory, storage, transfer and platform cards. Multiple GPUs keep separate memory capacities; unified memory is labeled shared. Full names, snapshot limitations and capture methods remain available in titles or disclosures.

After a helper restart, a compatible saved transfer capture can be displayed without running new probes or changing any benchmark. Its original timestamp and provenance remain intact, with **Saved capture** and `source: saved_capture`. Compatibility checks CPU/core counts, RAM capacity/modules, nonempty reported RAM clocks and all GPU names/memory/drivers. A clock or card change prevents reuse; independent captures take precedence over session captures.

Run and Results expose compact GPU, RAM/VRAM, storage and engine-setting badges. MTP badges distinguish requested, reported and verified states; unknown effective behavior stays unknown. Storage classes use reported media/bus evidence where available; an unspecified SATA device is not assumed to be an HDD. Full inventory and notes remain expandable. Bandwidth badges prefer an independent capture when available and identify it as **Independent probes**; hover for capture time and provenance. Each execution session retains its own probe measurements.

Results has three distinct views. **Overview** reports the system, coverage and, per model, peak prefill and decode speed, the change from the shortest to the longest completed prompt, the longest prompt completed with the first size that did not, and the change from the fewest to the most concurrent queries. Those trends are descriptive ratios of medians, not significance tests. **Graphs & comparisons** plots each ticked metric in its own chart, with all models together or one chart per model. **Tables & CSV** reports numerical medians and individual repeats. Graphs and tables share the metric, model and query-level toggles. Similar models are boxed together in the model list: first IDs that name the same model once the publisher, quantization and packaging are set aside ("4 variants"), then, among the rest, one family in several parameter counts ("4 sizes"). A box header shows or hides all of its models and **only** leaves just that box selected; a model with no sibling stays outside the boxes. The grouping reads names only and never changes what was measured. In Graphs, each benchmark in the chart key is a switch: click it to hide or show that benchmark's curves. Every ticked benchmark is on to begin with, an optional recorded condition such as an alternative storage run is offered switched off, and the notes above the charts count the passed tests that belong to switched-off benchmarks. A failed or skipped test that recorded fewer settings is filed under the measured condition it agrees with rather than shown as a separate condition; conditions are named as variants only when two of them measured the same model. A condition is defined by settings that can change a measured speed; where a label was reported from, a configuration hash that includes that provenance, and a session's test plan (sizes, repeats, selected cases) do not create one. Above the charts a banner counts the passed tests the current toggles draw. A test is counted as drawn when at least one ticked metric has a value for it; the rest are listed by cause (an unticked query count or prompt length, an unticked model, or a metric not recorded for that test) with a button for each remedy. Records made before request start offsets were kept have no whole-group prefill or decode rate above one query; those tests remain visible through per-request decode, time to first token, end-to-end output and completion time, and the affected charts say so. Recorded conditions retain visible checkboxes, selected/recorded totals and case/metric counts for the current selection. A condition with no matching model remains available as a choice but is omitted from that chart's legend.

Storage alternatives appear only when actual alternative inference rows are present. Installed drives or transfer probes do not imply a model was measured on them, and no storage type is required. **Compare recorded storage** selects the available primary/alternative conditions and experiment models, sets completion time, and opens Compare. SSD/NVMe observations retain separate identities, repeat medians, names and line styles. Default views retain primary observations. Median repeat values use the arithmetic middle for an even number of successes. Concurrent TTFT/prefill/decode metrics use per-query medians within each case; completion time covers all queries. For a single model, each chart includes the largest shared workload's exact values and repeat counts. Values use independent successful-repeat medians, matching the chart/table. Differences use matching successful repeats only; unequal subsets show the matched reference explicitly. Failure-only conditions remain in the legend/readout, and unpaired successes have no invented delta. Nearly overlapping curves can represent a measured small difference, as with IQ3_S in the recorded storage experiment.

**Table > All measurements** retains every selected repeat and exact query token counts/timings. Its **Export CSV** follows the selected conditions, models and query count. The Summary experiment's **Export both conditions CSV** exports the full frozen baseline and alternative, with per-query evidence in `request_metrics_json`. The helper's standard CSV API still exports primary measurements. Failed or unattempted cases never receive a paired speedup. See the [recorded 5060 Ti comparison](5060-ti-storage-comparison.md) for actual values, both 80k repeats and cache/placement conditions.


## Automatic fallbacks and substitutions

Wattever continues a benchmark when a test cannot run as requested, or when a sensor or count is missing. Each of these behaviors is recorded with the result, so a row always says how it was actually measured. Compare rows only when these fields match.

### Placement fallback (managed LM Studio)

**Model placement** (`gpu_offload`) is the placement you request; the default is **Prefer GPU** (`max`). With **Use CPU memory if needed** (`fallback_on_failure`, on by default), a model that fails to load is loaded again with less of it on the GPU, in this order:

| Attempt | Placement | Meaning |
| --- | --- | --- |
| 1 | the requested placement, `max` by default | every layer on the GPU |
| 2 | `auto` | LM Studio chooses the placement |
| 3 | `0.5` | half of the layers on the GPU, the rest on the CPU |
| 4 | `off` | CPU only |

- The requested placement is not tried twice, and the ladder stops at the first load that succeeds. Each attempt is a complete load with its own load timeout (900 seconds by default).
- Every result records the placement that loaded in `gpu_offload`. Results shows it as **Placement** in **Table > All measurements** and in the CSV export, and chart notes name any placement other than `auto`.
- A result with `gpu_offload` `0.5` or `off` ran partly or wholly on the CPU. Its speed, power and memory describe that placement, so compare it only with rows that have the same `gpu_offload`. Loads that failed before the successful one appear in the helper log, not in the result.
- When every attempt fails, the test is recorded as failed with `fail_kind: "load_failed"`.
- Fallback loads can take much longer than the full-GPU tests around them: a large context that does not fit in VRAM usually runs very slowly on the CPU and can reach the per-test timeout. To measure GPU capacity only, turn **Use CPU memory if needed** off, or send `fallback_on_failure: false`. A load that does not fit is then recorded as a failure at the requested placement.
- External endpoints have no placement fallback. The inference engine controls placement, and results record `gpu_offload` as `externally_managed`.

### Other automatic behaviors

| Behavior | When it applies | What Wattever does | How the result records it | Control |
| --- | --- | --- | --- | --- |
| Skip larger sizes after a capacity failure | A model fails to load, overflows its context or exceeds the model's context limit | Records the larger prompt sizes for that model, technique and query count as skipped | `status: "skipped"`, `fail_kind: "skipped_after_failure"` | **Skip larger sizes after a capacity failure** (`stop_model_after_failure`, on by default) |
| Move on after a timeout | A test reaches the per-test timeout | Skips the remaining repeats and larger contexts for that model and query count | `status: "skipped"`, `fail_kind: "skipped_after_failure"`; the timed-out row keeps `fail_kind: "timeout"` | **Move on after a timeout** (`skip_after_timeout`, off by default) |
| MTP pass without an MTP head | MTP is requested for a model whose file has no supported MTP head | Skips that model's MTP pass and keeps its standard pass; the placement ladder is not used | `status: "skipped"`, `fail_kind: "mtp_unsupported"` | Choose **Off** for MTP |
| Context allocated by LM Studio | LM Studio rounds the requested context or limits it to the model's maximum | Runs the test with the context LM Studio allocated | `requested_total_context` (requested) and `context_length` (allocated) | Choose prompt sizes and query counts whose total fits the model's context limit |
| Power source | No NVIDIA sensor is readable | Uses `powermetrics` on macOS, otherwise records no GPU power | `power_source`: `nvidia-smi`, `powermetrics` or `none`; `system_w_est` is always an estimate | None |
| CPU temperature source | No CPU package sensor is readable | On Windows, reads HWiNFO, then LibreHardwareMonitor, then Core Temp, then a live ACPI thermal zone; otherwise reports no value | `cpu_temp_source` names the sensor; `cpu_temp_note` says why a value is missing | Run one of the sensor tools |
| Output token count | The provider's stream carries no token usage | Leaves throughput unavailable instead of counting stream chunks | `metric_sources.completion_tokens`: `server_usage` or `unavailable`; an estimated count sets `completion_tokens_estimated` | Use a provider that reports usage |
| Endpoint name | An endpoint exposes no recognized service metadata | Names it Local, Private or Remote endpoint | The endpoint label | Set the optional **Display name override** |

See [troubleshooting](troubleshooting.md) for the matching symptoms and [API](api.md) for the request fields.

## Sessions and recovery

Each benchmark has one JSON file in `results/runs/`. The local helper supports same-file additions and repairs for both LM Studio and external endpoints. Reconnect the original external endpoint before repairing its tests; URLs and credentials are not saved. A timeout stops the generic run because Wattever cannot verify provider-side cancellation or unload. Inspect the engine before continuing.

Other failed requests on an external endpoint do not stop the run. The helper sends one short request to the same model. If the model answers, only that test failed and the benchmark goes on. If the endpoint answers but refuses the model, the test is recorded with `fail_kind: "model_unavailable"`, the model's remaining tests are recorded as skipped and the next model starts. If the endpoint does not answer within a minute, rejects the API key, or the check itself times out, the run stops with an explanation and the tests that never ran stay unrecorded, so the benchmark can be continued later. The test in flight when an endpoint disappeared is kept as a failure (`endpoint_unreachable`); include it with **Retry failed tests**. Each such row carries `endpoint_check` with the verdict and the HTTP status that decided it.

In Results, choose **Add / rerun tests**. Select an installed or served model to add it to the existing GPU benchmark, then review the workload and test counts. LM Studio offers Standard/MTP modes; external MTP stays provider controlled. Select one visible model and choose **Rerun selected model** to repeat its workload. Increase **Total repeats per test** to append repeat slots without replacing saved measurements. Set **Timeout per test** for new attempts, including individual repairs; each session and result retains its actual budget. In **Tests to update**, choose one saved model/size/query-count/repeat to repair only that test; the All measurements table also provides a **Repair repeat** button. **Add missing tests** preserves terminal cases; **Retry failed tests** includes failures and skips; **Rerun selected tests** includes successful cases. A replaced attempt moves to `previous_attempts` and is not averaged with its replacement. An exact snapshot is kept in `results/.history/`. Each execution has session settings, hardware inventory, measurement scope and provenance. Mixed benchmarks retain control and hardware attribution separately for each engine. Resume creates a new run for unfinished work. Additions and repairs require compatible hardware, selected GPU/driver and corpus. Managed tests also require the saved LM Studio version; external repairs require the saved endpoint identity. Otherwise start a new benchmark. External model loading remains under the engine operator's control.

To remove a model, select one benchmark and show only that model in the Models filter, then choose **Remove selected model** and confirm. Its measurements and planned workloads are removed; other models stay in place. A history backup preserves the original file. For the last model, use **Delete benchmark**. Shared community entries are read-only; these editing controls apply to the local helper's saved benchmarks.

Managed requests receive the configured per-test timeout. Prefill speed at shorter contexts does not shorten the budget for a larger context. The same whole-test budget applies while waiting for first output and during decode; output pauses do not impose a shorter hidden deadline. A timeout is a time limit, not physical freeze detection. The helper verifies managed model unload and worker exit before continuing; if verification fails, the run stops. Capacity failures can skip larger cases for that model/concurrency. By default, timeouts and transient request errors do not suppress subsequent repeats or larger contexts; a timed-out managed model is reloaded before another repeat. In the extension dialog's **Failure policy**, you can disable CPU placement fallback and opt to skip remaining repeats and larger contexts after a timeout. This records a practical time limit and explicit skips; it does not establish a hard VRAM allocation limit.

Older schemas and planner settings remain readable. An extended legacy run can contain sessions with different context planning; compare session settings rather than treating them as identical. See [API](api.md), [FAQ](faq.md), and [results guidance](../results/README.md).
