# Measurements and sessions

A case combines a model, Standard or MTP mode, prompt size, simultaneous query count and repeat. The runner records successful, failed and skipped cases; inability to load or fit a workload is useful capacity information. MTP requires a model with a supported bundled MTP head. Reasoning is disabled by default; settings and runtime versions accompany results.

Prefill throughput is prompt tokens divided by time to first token (TTFT), including overhead before the first token. Decode throughput is (completion tokens minus the first token) divided by the time from the first token to completion. Output token counts may be estimated when exact usage is unavailable. Group throughput for concurrent requests includes prefill and queueing and is distinct from per-request decode speed. Compare matching model builds, settings, corpus and protocol, and interpret differences in runtime placement and memory conditions.

The default per-test context allocation reserves prompt tokens, output budget, 512 tokens of headroom and a 5% prompt safety margin, subject to the model's per-request maximum. The shared KV allocation is the per-request capacity multiplied by simultaneous queries. Workloads are grouped by model. The default per-test policy reloads for each context and concurrency allocation; the optional fixed policy uses the largest planned allocation for a model and MTP mode, reducing reloads while changing memory conditions. More concurrency consumes more memory; large contexts can fail to fit.

NVIDIA telemetry uses `nvidia-smi` for the selected card's board power. macOS may use `powermetrics` for GPU and CPU rails with permission. These measure different boundaries; whole-system power is estimated, not a meter reading, and includes only the selected GPU sensor. GPU sensor selection does not direct LM Studio placement. Record placement separately. Missing sensor data remains unavailable. Hardware inventory is best effort and lists discoverable GPUs, CPU, memory and other equipment without serial numbers or unique IDs.

Each new benchmark has one JSON file in `results/runs/`. **Add / rerun tests** on an existing benchmark can select models and their Standard/MTP modes, prompt sizes and query counts. Choose an action and review the case counts in the preview: the default adds missing cases; retry failed also retries skipped cases; rerun selected tests replaces selected cases including successful ones. A replaced attempt is archived in `previous_attempts`, not averaged or included in a median with its replacement. Before changing the file, an exact snapshot is kept under `results/.history/`. Each execution records its own session settings and provenance. Resume creates a new run for unfinished work. Extension and resume require compatible hardware, selected GPU and driver, corpus and LM Studio version; when compatibility cannot be verified, start a new benchmark.

Prompt presets are 512, 5k, 10k, 20k, 40k, 80k, 100k, 120k, 150k, 200k and 260k tokens; concurrency presets are 1 through 10, 15, 20, 30, 40, 50, 75 and 100 simultaneous queries. Compare cases at matching dimensions.

Older schemas and planner settings remain readable. Extending a legacy benchmark can produce sessions with different context planning; compare session settings rather than treating them as identical. See [API](api.md), [FAQ](faq.md), and [results guidance](../results/README.md).
