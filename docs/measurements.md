# Measurements and sessions

The local helper supports managed LM Studio and generic OpenAI-compatible endpoints. Hosted browser mode uses a separate `browser-2` protocol; historical `browser-1` files remain readable. Browser/helper timings and historical estimates are not directly interchangeable. See [Browser mode](browser.md).

## Throughput and timing

A case combines a model, technique, prompt size, simultaneous query count and repeat. Successful, failed and skipped cases are recorded; inability to load or fit a workload is useful capacity information. The library reports successful, failed, skipped and cancelled counts separately; an unattempted skipped repeat is not counted as a measured failure. Managed LM Studio can schedule Standard/MTP modes when a supported bundled MTP head exists, and disables reasoning by default. Generic endpoint technique, reasoning, context allocation, KV cache and quantization are controlled by the inference engine. Their effective state is unknown unless documented separately by the operator; a scheduler technique label does not prove the server's MTP state.

`prefill_tps` is prompt tokens divided by client-observed time to first output (TTFT). It includes queueing, network, tokenization and any unobserved reasoning before streamed content arrives. It is not an isolated engine prefill compute measurement. Decode throughput uses output tokens attributable to the observed stream interval, excluding its first-token estimate, divided by that client interval through stream completion. A stream chunk can contain multiple tokens. Generic endpoint throughput remains unavailable when server usage counts are missing; it is not estimated by counting chunks. Legacy managed results may carry explicitly marked chunk-based estimates. Inspect `metric_sources` and estimated-token flags.

`timing_scope` records whether first output is content or reasoning, the output kinds observed, empty deltas before output, reasoning-token provenance and the decode token scope. `decode_token_count` records the numerator actually used. Reported hidden reasoning tokens are excluded from decode when they were not streamed. When empty pre-output deltas suggest hidden reasoning and its token count is unknown, decode throughput remains unavailable. Even without that signal, an endpoint that does not report reasoning may leave hidden work unverified. Compare equivalent timing boundaries rather than assuming completion usage always measures visible text. Decode energy per token uses the same scoped numerator.

A response with only one observable output event has no observed interval between output events; decode speed remains unavailable rather than timing the trailing usage message. Optional `endpoint_reasoning_effort` records a requested standard API control; it does not certify that the engine obeyed it.

Provider-reported engine counters, when supplied, are stored separately in `reported_timings`; do not combine them with client timings. `cached_prompt_tokens` records provider usage detail when available. Missing cache usage means unknown, not zero. A unique leading nonce reduces ordinary prefix reuse but does not prove that all provider caching, routing or warm state has been controlled. Record cache policy and compare equivalent conditions.

Group throughput for concurrent requests includes prefill and queueing and differs from per-request decode speed. `aggregate_completion_tps` divides successful requests' total output tokens by group wall time; it is not the sum of decode speeds. Concurrent requests have overlapping phases, so group power does not get an invented prefill/decode energy split. Compare matching model builds, settings, corpus, measurement source and protocol.

## Context and workload

For managed LM Studio, the default per-test allocation reserves prompt tokens, output budget, 512 tokens of headroom and a 5% prompt safety margin, subject to the model's per-request maximum. Shared KV allocation multiplies per-request capacity by concurrency. The per-test policy reloads for each context/concurrency allocation; the optional fixed policy uses the largest planned allocation per model and MTP mode, reducing reloads while changing memory conditions. Generic endpoint context estimates describe client workload planning only; configure the real context/KV allocation in the engine. More concurrency consumes more memory; large contexts can fail to fit.

Prompt presets are 512, 5k, 10k, 20k, 40k, 80k, 100k, 120k, 150k, 200k and 260k tokens; concurrency presets are 1 through 10, 15, 20, 30, 40, 50, 75 and 100. Compare cases at matching dimensions, output budget and repeat count. Close competing workloads and record relevant clock/power settings and runtime placement.

## Hardware, power and provenance

NVIDIA telemetry uses `nvidia-smi` for the selected card's board power. macOS may use `powermetrics` for GPU and CPU rails with permission. These have different boundaries. Whole-system power is estimated, not a meter reading, and includes only the selected GPU sensor. Selecting a sensor does not select inference placement. Generic endpoint power is unavailable unless `endpoint_inference_local: true` explicitly asserts that inference runs on the benchmark client. An externally loaded model prevents a verified unloaded-model idle baseline. Missing sensor data remains unavailable.

Hardware inventory is a best-effort, read-only snapshot of the benchmark client, not verified remote server hardware. Additive `metadata_schema_version: 1` metadata accompanies result `schema_version: 2`; historical files remain readable. Available fields include CPU/socket/core counts, RAM modules and reported clocks, GPU VRAM/driver, and current/max-reported PCIe generation and width. DIMM count does not establish active channels. PCIe snapshots can downshift while idle; reported maxima may reflect platform limits. `link_encoding_ceiling_bytes_per_second` is a derived one-direction ceiling after encoding only, excluding packet/system overhead. It is neither a measured DMA rate nor device-memory bandwidth. Unmeasured bandwidth remains null.

Memory topology is collected automatically without installing utilities. Windows reads SMBIOS through `GetSystemFirmwareTable`: populated Type 37 channel records take precedence; explicit Type 17 channel/slot labels provide a separately labeled firmware-layout inference. Linux uses populated EDAC channel locations where available. Other or incomplete reports remain unavailable. Raw firmware identifiers and slot labels are not retained. `memory.channel_topology` records the source, method, timestamp, populated channel count and independently detected active count, if supplied. **Populated channels do not prove the active controller interleave mode.** No count is inferred from DIMM quantity, CPU maximum specifications or bandwidth.

**This machine** and result badges distinguish firmware layout, OS reports and controller detection. **Refresh memory topology** runs the built-in probe. A later annotation on matching GPU, CPU, motherboard, RAM capacity and reported clocks retains its capture time and marks historical inference conditions unverified; original sessions and inference rows stay unchanged. Pending configuration checks prompt when their benchmark's GPU is reconnected. Channel counts and provenance are included in helper CSV exports.

Helper throughput and capability benchmarks also run separate transfer microbenchmarks before inference. **Measure transfer bandwidth** in the machine panel runs them independently. Choose **Storage test folder** on the drive holding your weights, or leave it blank to test the results volume; the folder path is excluded from saved public configuration. Storage → RAM reads a flushed 256 MiB temporary file three times in 8 MiB blocks at queue depth one, bypassing the OS page cache with Windows unbuffered I/O, Linux `O_DIRECT` or macOS `F_NOCACHE`. Device/controller caches may still contribute. File creation is excluded from read timing, and the temporary file is removed. This is sequential read throughput on the selected filesystem, not random expert-fetch performance or a measurement of other drives.

RAM → VRAM uses the selected NVIDIA adapter, mapped by PCI bus, through the CUDA driver. It times completed copies from a 64 MiB pinned host buffer, with warmup, three 2 GiB samples, synchronization and a readback check. It describes host-to-device transfers, not internal VRAM bandwidth or pageable-memory performance. The probe avoids starting when reported free VRAM is below 512 MiB. Unsupported hardware, insufficient resources and failed probes are recorded as unavailable rather than estimated. No inference models are loaded or unloaded by the probes. An isolated worker has a 75-second limit.

`hardware.transfer_bandwidth` records protocol `wattever-transfer-v1`, capture time, scope, method, raw byte/time samples and their median bytes/second; UI rates use decimal MB/s and GB/s. Throughput execution sessions retain their own profile. Generic remote endpoints characterize the benchmark client, not the inference server. Browser-only mode cannot perform these native probes. A later measurement can be attached to a saved benchmark only on matching hardware and GPU/driver; it is marked `measured_later_on_matching_hardware`, with historical inference conditions unverified. Original inference measurements and session metadata are preserved.

Optional `reproducibility` settings and `performance_claims` are user-reported public annotations kept separate from detected fields. Record engine/version, model revision, quantization, context, KV precision and MTP draft count when known, plus placement and competing workloads in reviewed notes. Wattever does not invent TFLOPS from GPU names or model quantization. A sourced compute claim must state arithmetic precision, execution path, dense/sparse behavior and whether it is an advertised peak, independent measurement or estimate. Integer INT4/INT8 claims use TOPS; floating-point FP4/FP8/FP16/BF16/FP32 claims use TFLOP/s. Quantized weight storage does not establish inference arithmetic precision.

Quantization storage format (`quantization`, such as `Q4_0`) is separate from the method (`quantization_method`, such as QAT, QAD or UD). LM Studio discovery combines its model catalog and display labels, and records `quantization_source` and `quantization_method_source`. Unknown methods stay unknown; a four-bit format alone does not establish QAT or post-training quantization. Results and model selection show both labels when available. Historical catalog annotations use `lmstudio_catalog_backfill`, which does not verify historical weight bytes.

Each result can also carry a public `model_configuration` and `configuration_id`. It distinguishes requested model alias, canonical checkpoint, automatically resolved opaque endpoint ID/display name, operator reports and control-plane evidence. Endpoint naming provenance is detected, inferred, operator override or unknown; it is not established by ports or model aliases. The private URL-to-ID registry is excluded from public outputs, and URLs are not hashed into route IDs. Unknown quantization, reasoning or MTP is explicit. A configuration hash verifies consistency of public fields; it does not verify endpoint weights, effective settings or inference location. Historical user-reported endpoint identities remain readable. Capability task accuracy uses a separate protocol/result family; see [capability evaluation](capabilities.md).

## Live telemetry and sustained observations

The helper samples whole-client CPU utilization and physical RAM usage independently of GPU sensor availability. GPU utilization, used VRAM, temperature, SM clock and board power describe the selected GPU. These measurements include competing processes and monitoring overhead; they do not isolate inference. VRAM percentage uses the selected adapter's reported capacity. Windows CPU temperature remains unavailable without an actual supported source; Linux may expose a CPU package sensor. Missing temperatures remain null, including on macOS without an available temperature source.

RAM usage means physical total minus OS-reported available memory on Windows and Linux. macOS uses total minus free/inactive pages and labels that availability boundary as an estimate. CPU utilization uses host CPU-time deltas, not load average. GPU snapshots are held briefly while fresh; failed/stale sensors do not become zero utilization.

Stored `telemetry.history` contains elapsed seconds, UTC timestamps, scope and up to 3,600 recent points with explicit ring-retention counts. At 150 ms this covers roughly nine minutes; older points can be dropped. `telemetry.summary` preserves all-run observed sample means, time-weighted means, maxima, first/last readings and coverage despite history eviction. Raw phase samples retain up to 72,000 rows; a phase older than that retention is flagged incomplete.

Time-weighted coverage excludes long sampling gaps. Peaks are observed maxima and can miss shorter spikes. Early/late 60-second means can overlap on short runs. Changes in temperature, clocks or load describe the observed workload/environment; they do not establish throttling or prove sustained model throughput. Compare repeat throughput at matching workload and placement alongside thermal/load traces. Separate graphs per selected metric avoid sharing incompatible units on one chart.

## RAM and storage comparisons

Transfer profiles also measure native RAM copy payload throughput with one worker and several workers. Each worker uses disjoint 64 MiB source and destination buffers; committed pages, one warmup pass, three timed samples and readback checks are included. The working set exceeds typical CPU caches. Reported bytes count copied payload: logical source reads plus destination writes equal twice that count, while actual DRAM traffic depends on caching and write allocation. This is a copy microbenchmark, not peak DRAM bandwidth or a channel-count measurement.

In Machine details, use **Additional storage folders** to compare drives during the same measurement; separate existing folders with semicolons. Each volume gets its own temporary unbuffered read test and raw samples. The selected primary volume remains separate. Paths stay private; volume letters, available device model names and measured rates can be shared. Inference may benefit differently because model loading, mmap faults, OS caches and CPU/GPU overlap affect its I/O.

Execution sessions retain their hardware snapshot and transfer profile, including reported RAM clocks. Later independent captures remain available in **Independent hardware measurements**. This preserves conditions across storage or memory-setting experiments.

The collapsed **This machine** header shows CPU, GPU, RAM and per-card VRAM. Expanded Run and saved Results inventories use the same grouped compute/memory, storage, transfer and platform cards. Multiple GPUs keep separate memory capacities; unified memory is labeled shared. Full names, snapshot limitations and capture methods remain available in titles or disclosures.

After a helper restart, a compatible saved transfer capture can be displayed without running new probes or changing any benchmark. Its original timestamp and provenance remain intact, with **Saved capture** and `source: saved_capture`. Compatibility checks CPU/core counts, RAM capacity/modules, nonempty reported RAM clocks and all GPU names/memory/drivers. A clock or card change prevents reuse; independent captures take precedence over session captures.

Run and Results expose compact GPU, RAM/VRAM, storage and engine-setting badges. MTP badges distinguish requested, reported and verified states; unknown effective behavior stays unknown. Storage classes use reported media/bus evidence where available; an unspecified SATA device is not assumed to be an HDD. Full inventory and notes remain expandable. Bandwidth badges prefer an independent capture when available and identify it as **Independent probes**; hover for capture time and provenance. Each execution session retains its own probe measurements.

Results has three distinct views. **Summary** reports primary case coverage, hardware conditions and a per-volume machine-transfer table. **Table** reports numerical medians and individual repeats. **Compare** plots the selected measurements, either overlaid or model by model. Table and Compare share model, metric, query-count and **Recorded conditions** filters; Summary's coverage remains the primary matrix. Recorded conditions retain visible checkboxes, selected/recorded totals and case/metric counts for the current selection. A condition with no matching model remains available as a choice but is omitted from that chart's legend.

Storage alternatives appear only when actual alternative inference rows are present. Installed drives or transfer probes do not imply a model was measured on them, and no storage type is required. **Compare recorded storage** selects the available primary/alternative conditions and experiment models, sets completion time, and opens Compare. SSD/NVMe observations retain separate identities, repeat medians, names and line styles. Default views retain primary observations. Median repeat values use the arithmetic middle for an even number of successes. Concurrent TTFT/prefill/decode metrics use per-query medians within each case; completion time covers all queries. For a single model, each chart includes the largest shared workload's exact values and repeat counts. Values use independent successful-repeat medians, matching the chart/table. Differences use matching successful repeats only; unequal subsets show the matched reference explicitly. Failure-only conditions remain in the legend/readout, and unpaired successes have no invented delta. Nearly overlapping curves can represent a measured small difference, as with IQ3_S in the recorded storage experiment.

**Table > All measurements** retains every selected repeat and exact query token counts/timings. Its **Export CSV** follows the selected conditions, models and query count. The Summary experiment's **Export both conditions CSV** exports the full frozen baseline and alternative, with per-query evidence in `request_metrics_json`. The helper's standard CSV API still exports primary measurements. Failed or unattempted cases never receive a paired speedup. See the [recorded 5060 Ti comparison](5060-ti-storage-comparison.md) for actual values, both 80k repeats and cache/placement conditions.


## Sessions and recovery

Each benchmark has one JSON file in `results/runs/`. The local helper supports same-file additions and repairs for both LM Studio and external endpoints. Reconnect the original external endpoint before repairing its tests; URLs and credentials are not saved. A timeout stops the generic run because Wattever cannot verify provider-side cancellation or unload. Inspect the engine before restarting.

In Results, choose **Add / rerun tests**. Select an installed or served model to add it to the existing GPU benchmark, then review the workload and test counts. LM Studio offers Standard/MTP modes; external MTP stays provider controlled. Select one visible model and choose **Rerun selected model** to repeat its workload. Increase **Total repeats per test** to append repeat slots without replacing saved measurements. Set **Timeout per test** for new attempts, including individual repairs; each session and result retains its actual budget. In **Tests to update**, choose one saved model/size/query-count/repeat to repair only that test; the All measurements table also provides a **Repair repeat** button. **Add missing tests** preserves terminal cases; **Retry failed tests** includes failures and skips; **Rerun selected tests** includes successful cases. A replaced attempt moves to `previous_attempts` and is not averaged with its replacement. An exact snapshot is kept in `results/.history/`. Each execution has session settings, hardware inventory, measurement scope and provenance. Mixed benchmarks retain control and hardware attribution separately for each engine. Resume creates a new run for unfinished work. Additions and repairs require compatible hardware, selected GPU/driver and corpus. Managed tests also require the saved LM Studio version; external repairs require the saved endpoint identity. Otherwise start a new benchmark. External model loading remains under the engine operator's control.

To remove a model, select one benchmark and show only that model in the Models filter, then choose **Remove selected model** and confirm. Its measurements and planned workloads are removed; other models stay in place. A history backup preserves the original file. For the last model, use **Delete benchmark**. Shared community entries are read-only; these editing controls apply to the local helper's saved benchmarks.

Managed requests receive the configured per-test timeout. Prefill speed at shorter contexts does not shorten the budget for a larger context. The same whole-test budget applies while waiting for first output and during decode; output pauses do not impose a shorter hidden deadline. A timeout is a time limit, not physical freeze detection. The helper verifies managed model unload and worker exit before continuing; if verification fails, the run stops. Capacity failures can skip larger cases for that model/concurrency. By default, timeouts and transient request errors do not suppress subsequent repeats or larger contexts; a timed-out managed model is reloaded before another repeat. In the extension dialog's **Failure policy**, you can disable CPU placement fallback and opt to skip remaining repeats and larger contexts after a timeout. This records a practical time limit and explicit skips; it does not establish a hard VRAM allocation limit.

Older schemas and planner settings remain readable. An extended legacy run can contain sessions with different context planning; compare session settings rather than treating them as identical. See [API](api.md), [FAQ](faq.md), and [results guidance](../results/README.md).
